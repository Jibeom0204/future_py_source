1클라이언트–서버 구조

웹은 요청하는 쪽(클라이언트)과 응답하는 쪽(서버)이 HTTP라는 약속으로 대화하는 구조다.

클라이언트 · 브라우저

요청을 보내는 쪽. 받은 HTML·CSS·JS를 해석해 화면을 그리고 JS를 실행한다.

브라우저가 실행하는 언어는 JavaScript뿐. 파이썬 코드는 브라우저에 도착하지 않는다.

서버 · 웹 서버 / WAS

요청을 기다렸다가(listen) 응답하는 쪽. 파일을 그대로 주거나(웹 서버) 프로그램을 실행해 결과를 만들어 준다(WAS).

DB 접속, 비밀번호(.env) 같은 민감한 처리는 서버에서만 한다.

약속 · HTTP

요청 1번에 응답 1번. 응답이 끝나면 서로를 기억하지 않는다(무상태, stateless).

서버는 요청 없이 먼저 말을 걸 수 없다. 실시간이 필요하면 폴링 · SSE · WebSocket을 쓴다.

4-B. 요청 실험: 서버 처리 시간과 브라우저 멈춤

요청 (브라우저 → 서버) 서버 처리 응답 (서버 → 브라우저)

4-D. SSR vs CSR: 폼 전송과 fetch 비교

A. 폼 전송 → 서버가 HTML 완성 SSR

{% if who %}서버가 만든 문장: 안녕하세요, {{ who }}님! (렌더링 #{{ render_no }} · {{ rendered_at.strftime('%H:%M:%S') }}){% else %}아직 보낸 이름이 없다. (렌더링 #{{ render_no }}){% endif %}

  • 주소창이 /?who=…로 바뀐다. GET은 쿼리스트링으로 보낸다.
  • 페이지 전체를 다시 받는다. ① SSR 시계와 렌더링 번호가 바뀌고 SSE도 다시 연결된다.
  • <b>굵게</b>를 입력해도 Jinja2가 자동 이스케이프해서 글자로만 보인다.

B. fetch POST → 브라우저가 HTML 완성 CSR

  • 주소창은 그대로이고 이 상자만 바뀐다. 렌더링 번호 #{{ render_no }}도 그대로다.
  • 서버는 JSON만 보내고, HTML은 JS가 템플릿 리터럴로 만든다.
  • 사용자 입력은 escape한 뒤 innerHTML에 넣는다 (XSS 방지).

5핵심 요약

  1. 구조브라우저(클라이언트)가 요청하고 서버가 응답한다. 브라우저는 HTML·CSS·JS만 실행하고, 파이썬은 서버에서만 실행된다.
  2. 통신TCP 소켓 위에 HTTP 형식(요청줄·헤더·본문 / 상태줄·헤더·본문)을 얹어 대화한다. 조회는 GET(쿼리스트링), 전송·변경은 POST(본문).
  3. 무상태HTTP는 요청이 있어야 응답한다. 서버가 먼저 보내려면 폴링(흉내), SSE(서버 → 브라우저), WebSocket(양방향)을 쓴다.
  4. HTML 처리정적 파일 → CGI print → Jinja2 템플릿(SSR)은 서버에서 HTML을 완성하고, CSR은 JSON을 받아 JS가 브라우저에서 DOM을 고친다.
  5. 비동기브라우저는 메인 스레드 하나로 화면과 JS를 처리한다. 통신을 비동기로 해야 서버를 기다리는 동안 화면이 멈추지 않는다.
  6. 서버 선택app.run()은 개발용이다. 운영에서는 waitress · gunicorn(+ Nginx)을 쓴다.
